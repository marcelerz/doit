### <a id="dup-24"></a>DUP-24 — Collections bypass createSharedStore, so separate browser tabs overwrite each other
*medium · `feature-extension` · effort L.* **Where:** `src/storage/sharedStore.ts:6-22`; `src/storage/sharedStore.ts:123-190`; `src/storage/settingsStore.ts:17`; `src/hooks/useTodos.ts:171`; `src/hooks/useNotes.ts:148`; `src/hooks/useEntityManager.ts:57`; `src/hooks/useSprints.ts:15`; `src/components/settings/ImportTab.tsx:27-30`. **Problem.** sharedStore was built because two tabs silently overwrote each other, but only settings uses it. The hooks then use store.use() and store.set, keeping StorageRecoveryScreen and the deleted-item cleanup. Writes become coalesced over 300ms and remain last-writer-wins inside that window. Decide this before DUP-01. **Done when.** A two-page Playwright spec adds a todo in tab A and then edits a todo in tab B, and asserts both changes survive a reload.

### <a id="bug-07"></a>BUG-07 — Collections are last-writer-wins across tabs; only settings is coordinated

### <a id="part-07"></a>PART-07 — Cross-tab sync reaches settings only, so other collections overwrite each other across tabs
*high · `bugfix` · effort L.* **Where:** `src/storage/sharedStore.ts:16`; `src/storage/sharedStore.ts:77`; `src/storage/settingsStore.ts:17`; `src/hooks/useTodos.ts:326`; `src/hooks/useNotes.ts:220`; `src/hooks/useReviews.ts:113`; `src/hooks/useSprints.ts:38`; `src/hooks/useEntityManager.ts:84`; `src/hooks/usePersistedState.ts:102`. **Problem.** sharedStore (commit c387c28) was built to stop two tabs silently overwriting each other, but createSharedStore has one caller: settingsStore. Todos, notes, reviews, sprints, people, projects, templates and the histories each keep a private useState copy, load once, and save the whole array on every change. None listens for BroadcastChannel, storage or visibilitychange events. Whichever tab saves last discards the other tab's edits. **Proposal.** Smallest fix: a subscribe/notify helper in sharedStore that posts {key, origin} on the existing 'doit-store' channel after each save, with each entity hook re-loading the key when another tab posts it. Larger option: move each collection onto createSharedStore, which also brings coalesced writes and the pagehide flush. Per-record keys stay out of scope. **Done when.** Two-page Playwright test, or jsdom with two hook instances and a BroadcastChannel mock: a todo added in tab A survives an edit saved afterwards in tab B.

### <a id="sup-05"></a>SUP-05 — Two open tabs silently overwrite each other's todos, notes, people, projects, reviews and sprints
*high · `bugfix` · effort L.* **Where:** `src/hooks/useTodos.ts:287`; `src/hooks/useTodos.ts:326`; `src/hooks/useEntityManager.ts:61`; `src/hooks/useEntityManager.ts:84`; `src/hooks/useNotes.ts:203`; `src/hooks/useNotes.ts:219`; `src/hooks/useReviews.ts:97`; `src/hooks/useReviews.ts:115`; `src/hooks/useSprints.ts:20`; `src/hooks/useSprints.ts:37`; `src/storage/sharedStore.ts:123`; `src/storage/settingsStore.ts:9`; `src/hooks/useTaskNotifications.ts:52`. **Problem.** Each data hook loads its collection once and writes the whole array on every change. Only settings use the store backed by BroadcastChannel. A tab or PWA window left open writes its stale array over another tab's work on its next edit, auto-archive or undo finalisation. The set of already-notified tasks is kept per tab, so with two tabs open every reminder fires twice. **Proposal.** Move todos, people, projects, notes, reviews and sprints onto createSharedStore, which re-reads on a channel ping, coalesces writes and flushes on pagehide. Add a per-key revision so a stale tab re-reads before it writes, and share the notified-task set the same way. Coordinate with the Duplication dimension's hook consolidation. SUP-24's second-tab notice covers the gap until then. If the diff grows too large, split it into one commit per hook. **Done when.** A unit test with two store consumers over one FakeAdapter and a mocked channel shows each sees the other's edit and neither overwrites it, and a two-page Playwright test confirms the same in the browser.

### <a id="sup-24"></a>SUP-24 — Restore, Clear All Data and Import do not tell other open tabs, which then write the old data back
*medium · `bugfix` · effort M.* **Where:** `src/components/settings/BackupTab.tsx:100`; `src/components/settings/StorageTab.tsx:236`; `src/components/settings/ImportTab.tsx:141`; `src/storage/sharedStore.ts:106`; `src/storage/sharedStore.ts:129`; `src/hooks/useTodos.ts:326`. **Problem.** Only settingsStore listens on the BroadcastChannel. After a restore or a clear in the settings tab, a second app tab still holds the old arrays in memory and writes them back on its next edit, auto-archive or undo finalisation, undoing the restore without any sign. **Proposal.** After restoreSnapshot, clearAllAppData and an import commit, broadcast a 'data-replaced' message on the existing channel. Every app tab then stops auto-saving and shows a banner that cannot be dismissed, 'Data was changed in another tab. Reload' (or simply reloads). Use the same channel to show 'DoIt is open in another tab', which covers SUP-05 until it lands. **Done when.** A two-page Playwright test restores in page A, edits in page B and reloads A: the restored data is intact and B shows the banner.

### <a id="doc-17"></a>DOC-17 — [Bug, cross-dimension] Cross-tab settings sync never reaches a tab that has not saved settings itself
*medium · `bugfix` · effort S.* **Where:** `src/storage/sharedStore.ts:16-18`; `src/storage/sharedStore.ts:38-49`; `src/storage/sharedStore.ts:100-108`; `src/storage/sharedStore.ts:129-133`. **Problem.** The header says a BroadcastChannel ping makes the other tabs re-read. getChannel(), which creates the channel and attaches onmessage, is called only from persistNow after a successful write. A tab that only reads settings never opens the channel, so it does not hear another tab's changes until it saves settings itself. **Proposal.** Open the channel eagerly in createSharedStore when running in a browser, by calling getChannel() next to channelListeners.set. Add a test in which a reader store that never writes receives a change posted by another origin. **Done when.** A sharedStore unit test with a mocked BroadcastChannel shows that a store which has never persisted re-reads and notifies when another origin posts its key.
