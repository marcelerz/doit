# 8. UI design review for usability

132 items: 24 high, 71 medium, 37 low. These findings were spot-checked by the synthesiser, not independently verified. Every item links to its full text; the unit and batch after each title say where the work is scheduled.

## Context

How this backlog was built. Four reviewer slices fed into it: visual system, views, overlays/forms/settings, and accessibility/keyboard. Together they produced about 150 findings, which merge into the 132 items below. Before keeping any high-priority item I opened its code myself. I re-read the TodoApp key handler (TodoApp.tsx:628-865), the four add dialogs (:1765-2228), closeAddOverlay (:620-626) and the header (:984-1043). I also re-read the Gantt window listener (GanttView.tsx:488-564), the Calendar document listener and its overlay inside calendarRef (CalendarView.tsx:364-409, 670-676, 973-1016), SmartInput's autocomplete and Enter handling (SmartInput.tsx:942-1224), Modal and useDialogFocus, ConfirmDialog and useConfirmDialog, NotesView.bulkDelete, ListView.selectAll and the batch-edit apply, the entity, sprint and settings delete and reset paths, WorkHoursTab's radio state, the auto-assign submit, backup import and cleanup, the Time Reports print CSS, the TodoItem checkbox, the tinted chips, the Tailwind 4 translate interaction, and two baselines (kanban, completed-list). Every high item held. I corrected two sub-claims; they are listed under dropped. Priority is normalised as follows. High means destructive or lossy with no safeguard, a core flow that keyboard users cannot complete, or information rendered effectively invisible. Medium means wrong behaviour that has a workaround, a real a11y or usability cost, or a foundation for later cleanup. Low means polish.

Where the problems concentrate. Keyboard handling is decentralised. About ten window or document keydown listeners run on every keypress: TodoApp.tsx:628, GanttView.tsx:551 (window), CalendarView.tsx:406, NoteDetailView.tsx:189 (window), FocusView.tsx:652, TutorialOverlay.tsx:385, useEscapeKey.ts:24 (window), useDialogFocus's Tab trap, plus CommandPalette, Subtasks and useKeyboardNavigation. None of them checks e.defaultPrevented or which layer is on top. React's own handlers run at the root before the document and window listeners, so a child calling preventDefault (SmartInput.tsx:1135) does not stop TodoApp's Escape branch from discarding the Add Todo draft. useDialogFocus.ts:68-87 already exports isTypingTarget and isActivationTarget; reuse them rather than writing new guards. Dialogs come in two generations. Modal.tsx gives role=dialog, aria-modal, a focus trap and restore at z-[60], but has no Escape handling and no portal: it renders inline, so a Modal inside a view is a DOM descendant of that view, which is why Calendar's handler hijacks its own overlay. About nine overlays are still hand-rolled fixed-inset divs at z-50. Destructive safeguards are uneven. The todo bulk delete, notes, reviews, people and project rows, and backup restore confirm first. The entity delete from the details overlay, all three sprint lifecycle actions, every settings Reset to Defaults, every settings list delete, and Batch Edit's default 'Clear all' do not. useConfirmDialog keeps a single dialog in state, so calling it in a loop keeps only the last call (NotesView bulk delete).

Colour is the second cluster. User hex colours are applied inline with three different text strategies: a fixed #333, getTextColor, and the hue itself on a tint of the same hue. getTextColor (colors.ts:65-103) uses a brightness heuristic that picks the lower-contrast option for mid tones. The default priorities define no colour (priority.ts:21-36), so the pastel #ffd4d4 from markerColors.ts:22 becomes the effective priority colour for the task checkbox border, the Kanban card stripe and every priority chip. That is why the main row control and the 'medium' chip are close to invisible in the baselines. Muted-text pairs have drifted, about 60 of them `dark:text-zinc-500`, because no semantic tokens exist: only --background and --foreground are defined, and nothing uses them. The third cluster is click-only records. Todos in List and Calendar, people, projects, notes, reviews, sprints, Gantt bars, click-to-edit titles, the RichTextEditor display mode and the Import drop zone all open through onClick on a non-focusable element. The in-repo patterns to copy are the Kanban card (KanbanView.tsx:1275-1285: role=button, tabIndex=0, Enter/Space) and the button roots of TodoListItem and NoteListItem. The fourth cluster is the undo infrastructure: undo actions and dependency-block notices are created app-wide in useTodos but rendered only by ListView.

What is in good shape and should be left alone. Modal plus useDialogFocus are the right base: extend them, do not fork them. globals.css:278-325 already handles revealing hover-only actions on focus-within and on hover:none, and already honours reduced motion, so do not solve either again per component. CommandPalette implements the full combobox and listbox pattern and is the template for SearchableDropdown and the SmartInput autocomplete. The Gantt and Calendar segmented controls use aria-pressed correctly. The Kanban keyboard move shares canTransition and canAcceptMore with drag and announces through a live region. ViewTabs shows labels at every width. UndoNotificationStack already separates destructive from neutral containers. The ServiceWorker toasts use role=alert. NotesTab and SprintsTab wire labels with id and htmlFor correctly. Commit d380139 set the muted-text and 11px floor conventions; the sweep items finish that work rather than inventing a new rule.

What an implementer must understand before touching anything. (1) Modal.close blurs the active element and defers onClose by a tick so that a RichTextEditor onBlur commits first. useEscapeKey.ts:6-13 explains that Escape was deliberately kept out of Modal for this reason, so any escape-stack or Modal onEscape change must keep the blur-then-close order. (2) In Tailwind 4.1, the translate-* utilities set the CSS `translate` property, which composes with keyframe `transform`. (3) The visual suite tolerates 1-2% pixel difference. Delete the baselines and regenerate them for every package that changes colour, type, spacing or icons, and compare the before and after images. (4) e2e/fixtures/todo-app.fixture.ts selects data-testid="todo-checkbox". Keep testids when a div becomes a button. e2e/smoke/accessibility-keyboard.spec.ts is the natural home for the new keyboard regressions. (5) settingsStore mirrors settings to localStorage (settingsStore.ts:17-28) so the inline theme script in layout.tsx can read them. (6) The `li button { min-width:0 }` rule in globals.css:349-354 cancels the 44px touch rule for every row action inside an &lt;li>. (7) The owner's constraint applies. Items marked feature-extension add behaviour. Items marked needs-decision must wait for the open questions. Nothing here removes a feature. Several items also belong to other dimensions (logic bugs, partly implemented features, strings, dead code); they are marked in the problem text so the central plan can deduplicate them.
