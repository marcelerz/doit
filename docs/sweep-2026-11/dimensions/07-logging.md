# 7. Missing, wrong or out-of-date logging

69 items: 16 high, 23 medium, 30 low. Each reviewer batch was checked against the code by an adversarial verifier (0 findings refuted outright, others corrected). Every item links to its full text; the unit and batch after each title say where the work is scheduled.

## Context

THIS DIMENSION COVERS TWO DIFFERENT 'LOGS'. (1) Diagnostic console output. There is no logger abstraction. git grep counts 87 console calls in src and public outside tests: storage.ts 32, public/sw.js 10, useServiceWorker.ts 8, useBackups.ts 7, backup.ts 5, browserApis.ts 4, sharedStore.ts 3, and 1-2 in about 15 other files. scripts/ has another 29, which are legitimate CLI output. (2) The user-facing activity log: utils/activityLogger.ts, utils/activityUtils.ts, components/shared/Activity.tsx, plus inline writers in useTodos, useNotes, useReviews, useSprints, useEntityManager and import.ts. Entries there are stored user data, shown in timelines and copied into backups. Changing their wording affects only new entries. There is no migration of old entries, and no entry type may be removed (owner constraint).

THE REAL RISK IS NOT A MISSING LOG LINE. It is that errors are swallowed and turned into default values, which are then persisted. Both storage adapters' getItem catch the error, console.error it and return null (storage.ts:16-22, 149-160). loadFromStorage turns null and unparseable JSON into the caller's default (storage.ts:332-345). Every hook then marks itself loaded, and its autosave writes [] or {} over the stored value. useTodos is worse: its catch sets loadError and its finally sets isLoaded, and the save effect at useTodos.ts:326-330 checks only isLoaded. So by the time StorageRecoveryScreen offers 'Download my data', doit-todos is already '[]'. Writes behave the opposite way: the adapters log and then rethrow, so every write failure is logged twice. saveToStorage resolves false and never rejects, but callers still chain dead .catch handlers. The load chains in useNotes, useReviews, useSprints and KanbanView have no rejection handler at all, so a malformed value silently switches off persistence for the session. Most of the high-priority items in this backlog (LOG-01, 02, 03, 07, 08, 09) are storage-truthfulness bugs found while checking what the log lines claim. They are bugs first and logging second.

WHERE THE PROBLEMS CONCENTRATE. Most of them are in src/storage/storage.ts (adapters, initializeStorage, the migrate functions, getStorageType, the persistent-storage functions), src/storage/backup.ts with src/hooks/useBackups.ts, src/components/settings/StorageTab.tsx, the load and save effects of the data hooks, and public/sw.js with src/hooks/useServiceWorker.ts. For the activity log they are in the editTodo diff (useTodos.ts:129-164 against TodoModel.metadata), Activity.tsx rendering, and noisy writers (review notes per keystroke, debounced autosaves, collapse toggles). There are three console prefix styles: none, '[PWA]' and '[SW]'. backup.ts/useBackups.ts and storage.ts/StorageTab.tsx emit identical strings, so the console cannot tell which module failed. The user-facing error channels are narrow. StorageErrorBanner is mounted only inside TodoApp, after its early returns. StorageRecoveryScreen is reached only by the todos loadError. app/error.tsx is the only error boundary, and there is no global-error.tsx.

HISTORY AN IMPLEMENTER MUST RESPECT. Commit ee18bdb deliberately removed the storage init, migration and backup lifecycle logs because they were noise. Commit 4a1ec8b removed dead .catch handlers but missed two. The owner clearly wants a quiet console, and the user CLAUDE.md forbids committing debug logs. So any trace this backlog adds (backend chosen, migration vN to vM, backups pruned, todos auto-deleted) belongs behind a debug gate. That is why a small logger (LOG-15) is justified: createLogger(scope) with debug/info gated off in production unless an internal flag key is set, warn/error always on, and warnOnce. No transports and no persistence. The UI-slice reviewer found no need of its own for a logger; the need comes from storage, hooks and the service worker. sw.js cannot import the bundle and needs its own tiny helper.

WHAT IS IN GOOD SHAPE AND SHOULD BE LEFT ALONE. Models and pure utils (autoDetection, chronoCustom, dateUtils, ganttScheduler and others) contain no logging and should get none, because they run during render. The silent catches in richText/keyHandlers.ts and richText/selection.ts are deliberate DOM guards on keystroke paths and must stay silent. saveToStorage's onStorageWriteError/isQuotaError channel is good design: reuse it, do not replace it. useTodos' .catch on its load chain is the right model for the missing handlers, but not its unconditional finally-then-save. loadFromStorage's guard against a literal 'null' is correct. RichTextEditor.tsx:973 and StorageRecoveryScreen.tsx:45 log reasonably. The useBackups and ThemeProvider catches look unreachable but guard `await loadBackups()` and a polling interval. They need better messages, not deletion.

BEFORE TOUCHING ANYTHING. (a) Changing getItem's swallow-and-return-null contract (LOG-02) ripples to every caller: StorageTab.calculateStorageUsage, estimateStorageQuota, StorageRecoveryScreen, isAlreadyMigrated, backup listing, TodoApp.tsx:458, StorageTab.tsx:153/264 and BackupTab.tsx:232. Catches that are dead today become live, so LOG-51 must follow that decision. Fire-and-forget calls that cannot reject today might start to. (b) Jest does not minify, so the constructor.name bug (LOG-07) cannot be reproduced by a unit test. The evidence is the gitignored production chunk build/static/chunks/c6eddffca2a5b004.js. The fix is a type field on the adapter. (c) Test fakes implement StorageAdapter, so interface changes touch the tests. (d) Do not write user content (todo text, note bodies, entity names, file contents) to the console. Keys, ids, counts, byte sizes and error names are fine. Whether entity names and file names are allowed is an open question. (e) Several activity fixes need one append point first (LOG-16), and characterisation tests first (LOG-29). (f) Findings that reviewers marked [OTHER] are included here, tagged 'Cross-dimension', so they are not lost: undo duplicate ids, duration snapping, note-title metadata loss, completion duration overwrite, timer transitions, TodoItem dead edit form. The central plan must deduplicate them against the Logic-bugs and Dead-code backlogs and give each one owner.

## Open questions

- [ ] Should debug and info logs be on only in development builds, or also switchable in production through an internal flag key such as doit-debug, so you can ask a user to turn it on for support?
- [ ] May console logs contain names the user typed, such as person and project names or imported file names? Or only keys, ids, counts, byte sizes and error names? This decides LOG-20 and LOG-50.
- [ ] When backup pruning by count or total size deletes backups younger than retentionDays, should the UI say so? Should a failed automatic backup trigger the storage error banner?
- [ ] When the stored data comes from a newer build (a downgrade), should the app go read-only or show the recovery screen? Or should it carry on as now with an accurate warning?
- [ ] If an entity rename cascade fails part-way, should the app finish renaming the entity (most references are already rewritten) or roll the rewritten references back?
- [ ] For core stores other than todos (people, projects, notes, reviews, sprints), should a load failure show the blocking recovery screen, or a non-blocking notice? And should templates and search/selection history use the lighter option?
- [ ] Which activity retention rule do you want: keep the newest N entries per entity (and which N), or fold older entries into a single summary entry?
- [ ] Which coalescing window should debounced edits use (for example 10 minutes), and which entry types should coalesce?
- [ ] Should collapsing or expanding a review entry keep producing an activity entry (reworded and coalesced), or stop being logged? Stopping would remove an existing behaviour.
- [ ] Should useNotes keep storing comment_added and comment_edited entries, which the timeline would de-duplicate, or stop writing them going forward?
- [ ] Should undo leave both the action entry and the undo entry in the log, and is 'Deletion/Completion/Archive undone' the wording you want?
- [ ] For 'Auto-Extend on Overtime': is the label right (extend only when tracked time exceeds the estimate) or the code (always set the duration to the tracked time)?
- [ ] Should stopping a timer ever move a card to In Progress, and should starting one affect a todo that is already completed?
- [ ] Gantt activity badge: should it show only when there is activity beyond the creation entry, or from some other threshold?
- [ ] Do you want a global 'Something went wrong' toast for errors and promise rejections that no error boundary catches?
- [ ] When a note is converted to a todo, should the todo's sourceNoteId field be set, or should only the activity entry link back to the note?
- [ ] Review comment activity types (comment_*) remain in the type union although review comments were removed: reinstate review comments, or mark those types as reserved?
- [ ] Should 'persistent storage not granted' be logged as a warning once per session, or stay silent (debug only)?
